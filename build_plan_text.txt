These decisions apply across the whole codebase. Most of the edge cases in later phases are
handled by getting these right once.
MONEY
Store amounts as integer paise (amountPaise: 1250000). Never use doubles.
Format with intlen_IN (₹12,50,000), with lakh/crore short forms on the dashboard.
All sums happen server-side in Functions. The client never writes totals.
DATES & TIME
Company timezone in config/company.timezone (default Asia/Kolkata).
A "working day" is a string key YYYY-MM-DD computed in that timezone. It is used for DPR
and attendance doc IDs.
Moments are stored as serverTimestamp() plus deviceTime. Trust the server; keep the
device value for audit.
Scheduled Functions declare timeZone explicitly.
DERIVED DATA
Triggers are at-least-once and may arrive out of order. Recompute from source (sum the
category's approved expenses) instead of increment() deltas where the set is small.
Where it isn't, use idempotent deltas keyed by event.id.
A nightly reconciliation job recomputes every total and logs any drift it corrects.
CHANGE-TOLERANT DATA
Every doc has schemaVersion, createdAt/By, updatedAt/By and deleted (soft
delete only).
Model parsing is tolerant: unknown keys are kept in extra, missing keys use defaults,
and a bad field never crashes a screen.
Lists and labels come from config/*, never from hard-coded enums (except system
states like approval status).
ACCESS
Custom claims hold onlyrole and companyId (the claims limit is 1000 bytes, so project
lists don't fit).
Project access uses projects/{pid}.memberIds[]. Rules check request.auth.uid in
get(project).data.memberIds, and child docs copy memberIds down to avoid extra

Offline architecture −
Firestore offline persistence is on (mobile default), with the cache size set to 100 MB.
Writes queue locally and sync automatically.
Firebase Storage does not queue uploads offline, so we build a local upload queue
(drift/SQLite table: localPath, storagePath, docRef, field, attempts, status),
drained by workmanager on connectivity and at app start.
A DPR doc is written immediately with photos: [{id, status:"pending"}]. The queue
uploads each file and updates it to {status:"uploaded", path}, and the CEO view
shows "photo syncing" for pending ones.
Photos are copied into app storage before queuing, so they survive the gallery or cache
being cleared.
A sync status bar shows "3 items waiting to sync". The supervisor can see and retry them;
items are never silently lost.
Logout is blocked, with a clear message, while the queue has unsynced items.
